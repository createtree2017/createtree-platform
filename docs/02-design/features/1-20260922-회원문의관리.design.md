# 회원 문의 관리 설계

## 데이터와 권한

`customer_inquiries`: id, user_id, title(1~100), content(1~3000), answer(nullable, 1~3000), answered_by, answered_at, answer_updated_at, created_at. 시간은 timestamptz. answer가 null이면 대기, 아니면 완료. 소유자별 최신 조회 인덱스와 미답변 부분 인덱스, 전체 최신 인덱스. 답변/답변자/시각의 일관성 CHECK. 회원 물리 삭제 시 문의는 cascade, 답변 관리자 삭제는 restrict로 이력 일관성 보존.

인증된 JWT로 ID를 확인하고 모든 요청에서 최신 DB 회원을 조회한다. 탈퇴/없는 계정은 401. 운영 관리자는 현재 DB memberType이 admin/superadmin이어야 한다. 병원 관리자는 본인 문의만 사용한다. 사용자 조회에는 user_id 조건을 SQL에 포함하며 타인 문의는 404. 응답에 비밀번호·토큰·관리자 개인정보를 포함하지 않는다.

## API

- POST /api/inquiries: title, content만 허용. 201 + 상세 응답.
- GET /api/inquiries: page(1 이상), limit(기본 20, 최대 20). items, page, total, hasMore.
- GET /api/inquiries/:id: 본인 상세.
- GET /api/admin/inquiries: 동일 페이지 + status=pending|answered|all, 기본 all.
- GET /api/admin/inquiries/:id: 작성자 이름·이메일을 포함한 상세.
- PUT /api/admin/inquiries/:id/answer: answer만 허용. 최초 답변 시각은 유지하고 수정 시각/담당자는 갱신. SQL 한 번으로 원자적 갱신.

모든 응답 no-store. 잘못된 ID/입력/페이지는 400, 무인증 401, 권한 부족 403, 없는 문의 404, DB 오류 503. 읽기만 기존 authenticated-fetch 인증 복구 사용. 쓰기는 자동 재시도하지 않는다.

## 화면과 상태

- /inquiries: 회원별 최신 목록, 20개 더 보기. /inquiries/new: 작성. /inquiries/:id: 상세. MY 계정관리 영역에 진입 링크.
- 관리자 /admin?tab=inquiries: 운영 관리자에게만 탭과 본문 노출. 기본 전체, 필터 변경 시 1페이지·선택 초기화. 모바일 카드 목록.
- 제목·내용·답변은 React 텍스트로 렌더링한다. 긴 문자열은 줄바꿈 처리. 요청 실패는 빈 상태와 구분하고 재시도 제공.
- 제출/저장 pending 동안 버튼 비활성화. 오류 때 입력 보존. 로그인 이동 전 회원별 sessionStorage 초안 저장, 성공 시 삭제. 사용자 계정이 바뀌면 초안·쿼리·편집 상태도 분리한다.
- 성공 후 사용자/관리자 문의 캐시 무효화. 사용자 자신의 문의에 관리자가 답변해도 다시 진입/포커스 시 최신 답변 조회.

## 후속: 미확인 답변 표시

- DB `answer_revision`/`read_answer_revision` (기본 0) 추가. 기존 답변은 버전 1, 확인 버전 0. 답변 저장 시 답변 버전 증가. `0 <= read_answer_revision <= answer_revision` 제약.
- GET `/api/inquiries/unread-count`: 현재 회원의 `answer_revision > read_answer_revision`인 답변 문의 수.
- PUT `/api/inquiries/:id/read`: 사용자가 실제 표시한 `answerRevision` 전달. 소유자만 확인 버전을 단조 증가시키며, 상세 조회 이후 수정된 더 최신 답변은 읽음 처리하지 않는다. GET에는 부작용을 넣지 않는다.
- MY 진입·포커스·30초 간격으로 최신 수를 확인. 0이면 숨김, 99 초과는 99+. 회원별 캐시, 조회 오류는 미확인 0으로 오인시키지 않음. 다른 기기에서 확인한 결과도 서버 기준 반영.
- 목록의 미확인 표시, 상세 표시 이후 읽음 처리. 읽음 저장 실패는 재시도 안내, 관리자 상세 조회는 사용자 읽음 상태에 영향 없음.
- 타임스탬프 정밀도/동시 수정 경쟁을 피하기 위해 숫자 버전을 사용한다. 답변 수정→읽음→다른 수정, 이전 버전 지연 읽음, 타인/미인증 요청을 검증한다.

## 구현과 검증

공유 입력/응답 계약, Drizzle 서비스, 라우터 팩토리, 인증 어댑터, 조회 훅, 독립 UI 컴포넌트로 분리한다. 기존 관리자 페이지는 탭 연결만 추가한다. 한정된 SQL migration을 사전 검증한 후 적용하며 전체 스키마를 강제 동기화하지 않는다.

실제 HTTP와 PostgreSQL 임시 테이블(단일 연결·트랜잭션 rollback), UI 텍스트 렌더링, 캐시 키·초안·오류 경계 테스트 및 전체 타입/빌드/인증 회귀를 수행한다. 운영 배포 및 브라우저 시각 검증은 별도이다.
