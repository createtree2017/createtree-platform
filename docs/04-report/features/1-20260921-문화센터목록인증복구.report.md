# 문화센터 목록 인증 복구 개발 보고

## 결과

참여가능/히스토리의 인증 실패·통신 오류가 빈 목록으로 표시되던 문제를 수정했다. 세션 또는 갱신 토큰으로 인증을 복구하고 GET/HEAD 요청을 한 번 재조회한다. 실제 고객 장애 시점의 응답/로그는 미확보 상태이므로 운영 장애의 단일 원인을 확정했다는 의미는 아니다.

## 구현

1. `MissionQueryNotice`: 조회 오류와 실제 빈 목록을 구분하고 기존 데이터가 있으면 유지한다. 재시도/로그인 버튼은 모바일 터치 크기를 확보한다.
2. `useMissionQueries`: 사용자/병원/등급별 캐시, 인증 완료 후 조회, 복귀/재연결 재조회, 일시 오류 1회 재시도를 적용한다.
3. `auth-recovery`: `/me`와 단일 `/refresh-token`의 복구 기준을 통합한다. 만료 JWT만으로 재발급하지 않으며 탈퇴/삭제 사용자를 거부한다. DB 오류는 인증 만료와 구분한다.
4. 일반·Google·Firebase ID 토큰 로그인에서 기존 14일 갱신 토큰을 발급한다. 로그아웃은 갱신 토큰을 DB에서 무효화한다. Google 로그인은 Passport 세션을 재생성하고 저장한다.
5. `authenticated-fetch`: 동시 갱신 합치기, 늦은 401 중복 갱신 방지, 읽기 1회 재전송, 취소 및 인증 상태 변경 경계 처리를 적용한다. 쓰기 요청은 자동 재전송하지 않는다.
6. 로그인 후 안전한 내부 원래 경로로 복귀한다. 최초 인증 확인이 서버/네트워크 오류로 실패한 경우 로그인 화면으로 오인 이동하지 않고 재시도를 안내한다.
7. 병원/등급 정보 변경 시 새 정보로 토큰을 맞춘다. 유효 JWT만으로 정보를 갱신하는 경우 원래 만료시간을 유지한다.

테스트는 격리된 새 Express 서버와 가짜 사용자 저장소를 사용한다. JSON/쿠키/401/503 응답, 만료·위조·탈퇴·계정 전환·동시 요청·쓰기 비재전송·오류 표시·캐시 분리를 검증했다. 테스트 출력의 503/HTML 오류 로그는 의도적으로 주입한 실패 시나리오다.

빌드 경고: 일부 모듈의 정적/동적 import 혼용, 500KB 초과 번들. 현재 빌드 성공을 막지 않으며 별도 성능 개선 대상이다. 로컬 Node는 v24.15.0이며 package.json의 배포 대상은 20.x이므로 실제 배포 런타임 검증과 구분한다.

## 사용자 영향 및 남은 검증

- 정상적인 인증 복구 중 추가 요청으로 잠깐 대기할 수 있다. 기존 목록은 유지한다.
- 세션과 갱신 자격이 모두 만료되었거나, 배포 전 로그인에 갱신 토큰이 없고 세션까지 사라진 사용자는 다시 로그인해야 한다.
- 서버 장애 때는 목록 소실 대신 오류 안내가 표시된다. 기존 목록은 최신 정보가 아닐 수 있음을 안내한다.
- 세션 저장소 자체의 영속화는 이번 범위가 아니다. 서버 재시작 후에는 갱신 토큰을 통해 JWT 읽기 인증을 복구한다. 세션 전용 API의 세션 복원까지 구현한 것은 아니다.
- 공통 `apiRequest`/기본 Query 함수와 `useAuth`를 수정했다. 별도의 직접 fetch/다른 API 클라이언트를 사용하는 모든 기능에 복구가 적용된 것은 아니다.
- 실제 모바일 브라우저, 실제 Google/Firebase 로그인, 운영 DB와 연결한 전체 서버 통합/운영 고객 재현 테스트는 미수행이다.
- GEMINI.md의 브라우저 정책: “브라우저 에이전트(browser_subagent)는 반드시 `!!테스트!!` 키워드가 포함된 경우에만 실행한다.” 이번 요청에는 해당 키워드가 없어 브라우저를 실행하지 않았다.
- 커밋·푸시·배포 및 DB 스키마/운영 데이터 변경은 수행하지 않았다.

## 수동/후속 화면 검증 절차

1. 개발 서버 실행 후 `http://localhost:5000/api/dev/auto-login`에 접속한다.
2. 문화센터 참여가능/히스토리에서 정상 목록과 탭 유지 여부를 확인한다.
3. API 네트워크 실패를 주입하고 오류 안내, 다시 시도, 기존 목록 유지 여부를 확인한다.
4. 시험 계정의 만료 JWT + 유효 세션/갱신 토큰 조합으로 재로그인 없이 목록 복구를 확인한다.
5. 갱신 자격까지 만료시켜 로그인 안내, 로그인 후 원래 문화센터 화면 복귀를 확인한다.
6. 서로 다른 두 시험 계정의 전환, 모바일 백그라운드 복귀/재연결을 검증한다. 운영 토큰을 로그/문서에 복사하지 않는다.

## 순차 무결성 재검증 결과 (2026-09-21 후속 요청)

사용자가 브라우저 테스트를 명시적으로 제외하고 코드 수준의 순차 검증을 요청했다. 기존 27개 테스트 통과를 확인한 후, 새 경계 조건 테스트 4개를 추가하여 실패를 재현하고 수정했다. 이후 총 40개 테스트로 확장했다.

### 발견 및 수정

1. 기존 쿼리 문자열이 있는 URL에 `?filter`를 중복 결합하던 문제를 `&filter` 처리로 수정했다.
2. `Headers` 객체/튜플 배열을 `Object.assign`으로 처리하면서 헤더가 누락되는 문제를 `new Headers`로 수정했다. GET 옵션과 취소 신호 처리도 정리했다.
3. 제어문자 또는 `..` 정규화로 로그인 복귀 주소 검사를 우회하는 경우를 차단했다.
4. `/me` 복구 함수가 Bearer 접두사 없는 Authorization 토큰을 받아 목록 인증과 다르게 동작하던 부분을 맞췄다.
5. 일부 Firebase 클라이언트가 서버의 필수 `idToken` 대신 사용자 프로필을 보내는 계약 불일치를 수정했다. `exchangeFirebaseIdToken`/`applyLoginResult`로 요청과 로그인 성공 후 캐시/토큰 처리를 통합했다.
6. Firebase 서버 처리에서 DB/세션 오류를 잘못된 토큰(401)으로 분류하지 않게 했다. 계정 전환 시 Passport 세션을 새로 만들며 세션 저장 후 인증 쿠키를 발급한다.
7. 문화센터 응답의 배열/기본 항목 구조를 확인하여 잘못된 200 JSON이 화면 반복문 오류로 이어지지 않도록 했다. 인증 응답에 새로 포함되는 토큰이 기존 콜백 로그에 노출되지 않게 했다.

### 검증 확대

- 실제 QueryObserver에 운영 문화센터 쿼리 옵션을 적용하여 로그인 전 비활성화, 계정/병원별 키, 복귀/재연결, 신선한 데이터의 불필요한 재조회 방지, 503 제한 재시도, 401 반복 차단을 확인했다.
- 실제 express-session/Passport 메모리 세션과 HTTP 쿠키를 사용해 프론트 `authenticatedFetch` → 실제 갱신 핸들러 → 목록 재조회 연동을 검증했다. 세션 저장소 소실 후 갱신 토큰 복구와 로그아웃 후 401도 확인했다. 목록/로그인/로그아웃 엔드포인트 및 사용자/갱신 저장소는 격리한 테스트용 구현으로, 운영 DB 통합 테스트와 다르다.
- 동시에 기다리던 조회 중 하나의 취소가 다른 조회를 깨뜨리지 않는지, 잘못된 갱신 응답 이후 다음 요청이 복구되는지도 확인했다.
- 신규 테스트를 포함한 전체 타입 검사에서 발견한 테스트 fixture의 누락 필드 2건을 보완하고 다시 통과했다. 애플리케이션 기본 타입 검사에는 오류가 없었다.
- 최종 40개 테스트/전체 소스 및 신규 테스트 타입 검사/프론트·서버 빌드/586개 TS·TSX 구문/환경·스킬/설치 의존성 검증이 통과했다.

### 실행하지 않은 검증

- 브라우저: 사용자 명시 지시에 따라 미실행.
- 실제 외부 OAuth/Firebase 인증 및 운영 DB: 로컬 격리 테스트 범위에서 제외.
- 기존 `server/tests/security-image-proxy.test.ts`: Jest/supertest가 설치·설정되어 있지 않아 실행하지 못했다. 구문 검사에는 포함했다.
- `scripts/test-*` 중 운영 DB 변경, 메일/푸시 발송, 외부 AI 호출이 포함된 스크립트는 단순 코드 검증 목적으로 실행하지 않았다. 구문 검사는 수행했다.
- Node 20 배포 런타임 검증: 로컬은 Node 24.15.0으로, 해당 배포 런타임 자체는 실행하지 않았다.
