## 최고관리자 로그인 점검·복구

### 증상과 확인 결과

- 사용자는 전날 개발 이후 로그인 불가, 비밀번호 변경 완료 화면 이후에도 로그인 API 401, 예전 Replit 페이지 노출을 제보했다.
- 전날 인증 변경 커밋 `5887a3b`는 인증 복구와 문화센터 목록 오류 처리를 보강했다. 만료 JWT만으로 인증을 복구할 수 없도록 된 점을 확인했으며, 이를 이번 비밀번호 불일치의 원인으로 단정하지 않았다.
- 재설정 대상은 `ct.createtree@gmail.com`, 실제 로그인 시도 계정은 `9059056@gmail.com`으로 서로 달랐다. 한 계정의 비밀번호 변경 완료가 다른 최고관리자 계정의 비밀번호 변경을 의미하지 않는 것이 이번 실패 조사에서 확인된 핵심이다.
- 사용자가 최초 최고관리자로 지정한 `9059056@gmail.com`은 DB 사용자 ID 24, `memberType=superadmin`으로 확인했다. 명시 요청에 따라 해당 계정에 한해 bcrypt 비용 10으로 해시한 임시 비밀번호를 저장했다.
- 변경 후 실제 운영 `/api/auth/login`과 `/api/auth/me`가 모두 HTTP 200을 반환하고 superadmin 권한을 유지하는 것을 확인했다. 이후 문의 기능 개발 과정에서 인증 코드를 추가로 변경하지 않았다.
- 비밀번호 원문·해시·재설정 토큰·JWT·쿠키·환경변수 값은 이 인수인계에 기록하지 않는다. 사용자는 임시 비밀번호를 추후 직접 변경할 예정이라고 했다.

### 예전 Replit 링크와 로그의 관계

- `client/src/pages/auth.tsx`의 홍보 영역에 `https://createtreeai.replit.app/` 링크가 남아 있음을 확인했다. 해당 페이지의 비활성 안내와 폰트 404는 로그인 API의 401과 별개이다. 링크 자체는 이번 작업에서 수정하지 않았다.
- 현재 앱 로그인은 자체 `/api/auth/login`, 로그인 상태 조회는 `/api/auth/me`를 사용한다. Firebase 초기화 성공 로그만으로 이 앱 로그인 성공 여부를 판단하면 안 된다.
- 비로그인 상태의 `/api/auth/me` 401과 자격 증명 검사 단계의 `/api/auth/login` 401을 구분한다. PWA 배너·메타 태그 경고 및 기존 `auth_status` 쿠키 표시만으로 서버 인증 성공을 판단하지 않는다.
- 관련 코드: `server/routes/auth.ts`, `server/services/auth-recovery.ts`, `client/src/pages/auth.tsx`, `client/src/pages/ResetPassword.tsx`, `client/src/lib/login-session.ts`, `client/src/lib/authenticated-fetch.ts`.

## 배경과 결정

고객 문의를 사이트 안에서 접수하고 운영 관리자가 간단히 답변하도록 요청받았다. 사용자가 최소 범위 계획의 구현·오류 수정·코드 기반 테스트 완료를 명시적으로 요청했다. 기존 인증, Railway DB, React UI를 재사용하고 별도 서비스나 환경변수를 추가하지 않았다.

비회원 문의는 사용자가 이메일로 처리한다. 비공개 회원 문의와 답변 1개를 구현하고, 첨부·추가 댓글·메일/푸시 알림·사용자 수정/삭제는 제외했다. 화면 내 미확인 답변 뱃지는 후속 요청으로 추가했다. 문의 소유권과 현재 운영 관리자 권한을 서버에서 검증한다.

## 주의사항과 알려진 한계

- DB 테이블은 이미 반영했지만 운영 화면/API 코드는 아직 배포 전이다. 배포 후 사용자와 관리자 화면에서 최종 접수/답변 흐름을 확인한다.
- 새 테이블만 추가했다. 운영 테스트 문의·메일·푸시를 생성하지 않았다.
- `test:inquiries`는 DATABASE_URL/JWT_SECRET 설정과 DB TEMP 권한이 필요하며, 임시 테이블 격리를 확인한 뒤 fixture를 만든다.
- 문의 내용은 sessionStorage에 회원별 초안으로 저장된다. 같은 탭의 재로그인에서 복원하며 탭을 닫으면 보존을 보장하지 않는다.
- 답변 수정 이력을 누적하는 댓글 기능은 없다. 답변 본문은 최신 1개, 최초 답변일과 최종 수정일을 보관한다.
- 기존 인증 시스템 자체를 변경하지 않았다. 만료된 쓰기 요청은 자동 재전송하지 않는다.
- 빌드의 기존 큰 번들/혼합 import 경고는 남아 있다.
- 기존 미추적 `20260612-모바일크롬PWA앱홈스크롤불가수정.인수인계.md`는 수정하지 않았다.

## 후속: 미확인 관리자 답변 뱃지

사용자가 MY의 나의 알림처럼 문의 답변 도착을 알 수 있는 뱃지를 요청했다. 읽지 않은 답변 문의 수를 빨간 숫자와 `N개 안읽음`으로 표시하고, 목록에 새 답변을 표시한다. 사용자 상세의 표시된 답변을 확인하면 읽음 처리한다. 관리자 조회와 GET 요청에는 읽음 저장 부작용이 없다.

### 변경과 이유

- `shared/schema.ts`, `shared/inquiries.ts`, `server/services/inquiries.ts`, `server/routes/inquiries-router.ts`: 답변 버전·확인 버전과 미확인 개수/읽음 API 추가. 숫자 버전으로 타임스탬프 정밀도 차이와 동시 답변 수정 경쟁을 방지한다. 오래된 읽음 요청은 더 최신 답변을 읽음 처리하지 않는다.
- `db/migrations/20260922_add_inquiry_read_revisions.sql`, `scripts/apply-customer-inquiries.ts`: 읽음 버전 2컬럼·제약·부분 인덱스 추가. 기존 답변은 버전 1/확인 0으로 초기화하며 문의/답변 본문은 변경하지 않는다. 운영 DB 적용 후 11컬럼·5인덱스 확인.
- `client/src/components/inquiries/InquiryMenuItem.tsx`(신규): 기존 노란 테두리를 유지하고 문의 아이콘·숫자·미확인 안내 추가. MY 진입/포커스/30초 주기로 서버 상태 조회, 오류를 0건으로 오인시키지 않는다.
- `client/src/components/inquiries/InquiryReadReceipt.tsx`(신규): 사용자 상세 표시 후 화면이 보이는 경우 실제 본 답변 버전만 저장. 실패 시 수동 재시도 안내.
- `client/src/hooks/useInquiries.ts`, `client/src/components/inquiries/InquiryParts.tsx`, `client/src/pages/profile.tsx`, `client/src/pages/inquiries.tsx`: 회원별 숫자 캐시, 읽음 후 갱신, 목록 새 답변 표시 연결.
- 기존 서버/클라이언트 문의 테스트, Plan/Design/Report, 플랫폼 스킬에 새 흐름 반영.

- 브라우저 자동 실행, 메일·푸시 발송, 커밋·푸시·운영 코드 배포는 하지 않았다. 새로운 스키마는 이미 운영 DB에 반영되어 코드 배포 시 사용할 수 있다.

Skill Impact Check: 신규 API와 읽음 버전 처리 기준을 플랫폼 스킬에 반영했다. 일반 운영 권한 정책 변경은 없다.

## 다음 환경에서 이어받을 때

1. 이 문서와 연결된 Plan/Design/Report를 함께 확인하고 develop의 문의 기능 커밋을 기준으로 이어받는다. 기존 미추적 `docs/05-devlog/20260612-모바일크롬PWA앱홈스크롤불가수정.인수인계.md`는 이번 작업과 무관하여 커밋 대상에서 제외했다.
2. DB는 이미 적용되어 있다. 재확인은 `npx tsx scripts/apply-customer-inquiries.ts` 기본 실행으로 읽기 전용 검사한다. 검증된 두 migration 외 전체 스키마 강제 동기화를 반복하지 않는다.
3. 로컬 주소는 `http://localhost:5000/profile`, 사용자 문의는 `/inquiries`, 관리자 문의는 `/admin?tab=inquiries`이다. 서버 시작은 저장소의 기존 개발 실행 구성을 사용한다.
4. 현재 읽음 계약은 `answerRevision > readAnswerRevision`이다. GET/관리자 조회는 읽음 처리하지 않으며 사용자 상세에서 실제 표시한 버전만 PUT으로 저장한다. 새 답변을 읽지 않은 상태로 재현하려면 관리자 답변 작성/수정 후 사용자 상세를 열기 전에 MY를 확인한다.
5. 코드 검증은 `npm run test:inquiries`, `npm run test:auth-recovery`, `npm run check`, `npm run build`를 사용한다. 같은 검증이 통과한 뒤 문서만 변경한 이번 푸시에서는 테스트를 중복 실행하지 않았다.
6. 검증 로그는 작업 PC 임시 폴더의 `ct-inquiry-badge-node20.log`, `ct-inquiry-badge-build.log`에 있다. 마지막 확인 결과는 테스트 65개 통과·실패 0·건너뜀 0, 프론트/서버 빌드 성공이다. 로그는 Git에 포함하지 않는다.
7. 운영 배포 완료 여부를 확인한 뒤 실제 회원 문의 → 관리자 답변 → MY 뱃지 → 사용자 읽음 순서를 확인한다. 브라우저 자동 검증은 별도 `!!테스트!!` 요청 범위에서 수행한다. Git 푸시 성공만으로 운영 화면 검증 완료를 보고하지 않는다.

## 푸시 요청 반영

사용자가 `!!푸시!!`를 명시했고 오늘 전체 작업의 인수인계 저장도 요청했다. 이 문서를 포함한 회원 문의 기능·후속 개선·테스트·migration·플랫폼 스킬 변경을 `origin/develop`에 반영한다. 기존 기능과 관계없는 파일 및 비밀번호 변경용 임시 자료는 포함하지 않는다. 실제 커밋과 푸시 결과는 Git 이력 및 작업 최종 보고를 기준으로 확인한다.

## 푸시 이후 후속: 문의 화면 상단 MY 제목·이동 경로 수정

- 앞선 문의 기능과 통합 인수인계는 커밋 `215a2da`로 `origin/develop`에 푸시했고 원격 커밋 일치까지 확인했다.
- 이후 사용자가 문의 화면 상단에 `MY` 대신 `AI이미지생성`이 보이는 문제를 제보했다.
- 원인: `client/src/App.tsx`의 공통 Layout `getSectionTitle()`에서 `/inquiries`가 어느 메뉴에도 매칭되지 않아 AI 생성 기본값을 반환했다. 동일 결과를 쓰는 상단 제목 링크와 뒤로가기 경로도 `/`로 잘못 지정되었다.
- 수정: 문의 목록 `/inquiries`, 작성 `/inquiries/new`, 상세 `/inquiries/:id`를 MY 하위 화면으로 먼저 판별한다. 제목은 관리자 메뉴 설정의 `my-page` 제목을 따르고, 데이터 로딩 전/미설정 시 `MY`를 사용한다. 상단 제목 링크와 뒤로가기는 `/profile`로 연결한다.
- 기존 문의 본문 제목·작성/답변·읽음 처리·DB/API는 변경하지 않았다. 공통 Layout을 사용하므로 모바일과 데스크톱 모두 같은 제목/경로를 적용한다.
- ✅ `npm run check -- --pretty false` 통과. 문의 경로 및 공통 헤더/뒤로가기 사용처를 코드로 확인했다.
- 브라우저 자동 검증은 수행하지 않았다. 로컬 검증 후 사용자가 별도 `!!푸시!!`를 요청하여 이 후속 수정과 인수인계를 develop 커밋/푸시에 포함한다. 운영 배포 완료 여부는 별도 확인 대상이다.
- Skill Impact Check: 기존 문의 화면의 누락된 메뉴 분류 수정이며 신규 API·DB 계약·개발 명령·운영 정책 변경이 없어 스킬 추가 수정은 필요하지 않다.
